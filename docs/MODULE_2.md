# Module 2 — Project, Team & Task Management

## Goal

The objective is to transform the authenticated DevFlow foundation into a usable project-management workspace where users can create projects, manage members, create and organize tasks, assign work, and manage task workflow through a Kanban board.

## SCOPE

### Projects
- Create project
- Read/list projects
- Read single project
- Update project
- Delete project
- Project owner
- Project members
- Project status
- Project priority
- Start date
- Due date
- Created/updated timestamps

### Team / Membership
- Add members to projects
- Remove members
- View project members
- Establish project membership boundaries
- Owner vs member distinction where required
- Prevent unauthorized users from accessing project data

*Note: Do not implement full RBAC in Module 2. Full role-based access control belongs to Module 3. However, Module 2 MUST establish the minimum project-access authorization needed to prevent unauthorized project/task access.*

### Tasks
- Create task
- Read/list tasks
- Read single task
- Update task
- Delete task
- Project relationship
- Assignee
- Status
- Priority
- Labels
- Due date
- Created/updated timestamps

### Kanban
Define a board with persisted task status. We will use a small controlled set of statuses:
- `todo`
- `in_progress`
- `review`
- `done`

Dragging a task between columns must persist its new status through the backend.

## DATABASE DESIGN

### Project Model
- `_id`: ObjectId, auto-generated
- `name`: String, required, trimmed, max length 100
- `description`: String, optional, max length 1000
- `owner`: ObjectId (ref: 'User'), required, indexed
- `members`: Array of ObjectIds (ref: 'User'), default `[]`, indexed
- `status`: String, enum (`planning`, `active`, `on_hold`, `completed`, `archived`), default `planning`
- `priority`: String, enum (`low`, `medium`, `high`, `urgent`), default `medium`
- `startDate`: Date, optional
- `dueDate`: Date, optional, must be >= `startDate` if both provided
- `createdAt`: Date, generated by Mongoose timestamps
- `updatedAt`: Date, generated by Mongoose timestamps

### Task Model
- `_id`: ObjectId, auto-generated
- `project`: ObjectId (ref: 'Project'), required, indexed
- `creator`: ObjectId (ref: 'User'), required, derived from token
- `title`: String, required, trimmed, max length 200
- `description`: String, optional
- `status`: String, enum (`todo`, `in_progress`, `review`, `done`), default `todo`, indexed
- `priority`: String, enum (`low`, `medium`, `high`, `urgent`), default `medium`
- `assignee`: ObjectId (ref: 'User'), optional, indexed
- `labels`: Array of Strings, default `[]`
- `dueDate`: Date, optional
- `createdAt`: Date, generated by Mongoose timestamps
- `updatedAt`: Date, generated by Mongoose timestamps

## DATABASE RELATIONSHIPS

User
 |
 +---- owns ----> Project
 |
 +---- member of -> Project
                      |
                      +---- has ----> Task
                                       |
                                       +---- assigned to ---> User

- **Project.owner**: The creator of the project. Controls the project, controls membership, and can manage all project tasks.
- **Project.members**: Users authorized to view the project, create tasks, update tasks, delete tasks, and be assigned tasks.
- **Task.project**: The parent project containing the task.
- **Task.creator**: The user who originally created the task.
- **Task.assignee**: A project member responsible for the task.

**Deletion Rules**:
- If a project is deleted, all associated tasks are deleted.
- If a user is removed from a project, they are automatically unassigned from any incomplete tasks within that project.
- Avoid introducing unnecessary cascade behavior outside of these basic constraints.

## AUTHORIZATION BOUNDARIES

| Operation | Owner | Member |
|---|---|---|
| View project | ✅ | ✅ |
| Update project details | ✅ | ❌ |
| Delete project | ✅ | ❌ |
| Add member | ✅ | ❌ |
| Remove member | ✅ | ❌ |
| View tasks | ✅ | ✅ |
| Create task | ✅ | ✅ |
| Update task | ✅ | ✅ |
| Delete task | ✅ | ✅ |

- Unauthenticated users cannot access project or task APIs.
- Only authenticated users can create projects (becoming the owner).
- Users cannot assign arbitrary users to tasks unless the target user belongs to the project (explicit backend rule).
- Users cannot move/edit tasks belonging to projects they cannot access.
- The backend always enforces project membership.

## API DESIGN

All endpoints require authentication (valid `devflow_access_token` cookie).

### Projects

**GET /api/projects**
- **Purpose**: List projects the user owns or is a member of.
- **Response**: `200 OK` `{ "success": true, "data": { "projects": [...] } }`

**POST /api/projects**
- **Purpose**: Create a new project.
- **Body**: `{ "name", "description", "status", "priority", "startDate", "dueDate" }`
- **Response**: `201 Created`

**GET /api/projects/:projectId**
- **Purpose**: Get project details (if authorized).
- **Response**: `200 OK`

**PATCH /api/projects/:projectId**
- **Purpose**: Update project details.
- **Authorization**: Owner or authorized member (rules TBD based on exact fields).
- **Response**: `200 OK`

**DELETE /api/projects/:projectId**
- **Purpose**: Delete a project.
- **Authorization**: Owner only.
- **Response**: `200 OK`

### Members

**GET /api/users/search**
- **Purpose**: Search for users by name or email for project member selection.
- **Query Parameters**: `?q=search_term`
- **Response**: `200 OK` (returns minimal safe user info like id, name, email)

**GET /api/projects/:projectId/members**
- **Purpose**: List all members of a project.
- **Response**: `200 OK`

**POST /api/projects/:projectId/members**
- **Purpose**: Add a member to a project.
- **Authorization**: Owner only.
- **Body**: `{ "email" }` (Uses email for easier lookup).
- **Response**: `200 OK`

**DELETE /api/projects/:projectId/members/:userId**
- **Purpose**: Remove a member from a project.
- **Authorization**: Owner only (or self-removal).
- **Response**: `200 OK`

### Tasks

**GET /api/projects/:projectId/tasks**
- **Purpose**: List all tasks for a project.
- **Response**: `200 OK` `{ "success": true, "data": { "tasks": [...] } }`

**POST /api/projects/:projectId/tasks**
- **Purpose**: Create a task in a project.
- **Body**: `{ "title", "description", "status", "priority", "assignee", "labels", "dueDate" }`
- **Response**: `201 Created`

**GET /api/tasks/:taskId**
- **Purpose**: Get task details.
- **Authorization**: Must have access to parent project.
- **Response**: `200 OK`

**PATCH /api/tasks/:taskId**
- **Purpose**: Update task details, including status for Kanban drag-and-drop.
- **Body**: `{ "title", "status", "priority", "assignee", ... }`
- **Response**: `200 OK`

**DELETE /api/tasks/:taskId**
- **Purpose**: Delete a task.
- **Response**: `200 OK`

## PROJECT VALIDATION

**Project**:
- `name`: Required, trimmed, max 100 characters.
- `description`: Optional, max 1000 characters.
- `startDate` & `dueDate`: Valid dates. `dueDate` cannot be earlier than `startDate`.
- `status`: Restricted to `planning`, `active`, `on_hold`, `completed`, `archived`.
- `priority`: Restricted to `low`, `medium`, `high`, `urgent`.

**Task**:
- `title`: Required, trimmed, max 200 characters.
- `description`: Optional.
- `status`: Restricted to `todo`, `in_progress`, `review`, `done`.
- `priority`: Restricted to `low`, `medium`, `high`, `urgent`.
- `assignee`: If provided, must be a valid ObjectId and the backend strictly enforces that the user belongs to the project.

## PROJECT STATUS / PRIORITY

**Project Statuses**:
- `planning`: Initial setup phase.
- `active`: Work is currently being done.
- `on_hold`: Paused temporarily.
- `completed`: Finished successfully.
- `archived`: Read-only historical record.

**Task Statuses** (Aligned with Kanban columns):
- `todo`
- `in_progress`
- `review`
- `done`

**Shared Priorities**:
- `low`, `medium`, `high`, `urgent`.

## TEAM MEMBERSHIP

- **Identification**: Members are added using their `email` address.
- **Duplicates**: Attempting to add an existing member returns a `409 Conflict` or graceful `200 OK` with a message.
- **Non-existent Users**: Attempting to add an email not registered in DevFlow returns `404 Not Found`.
- **Removal**: The project owner can remove any member. Members can remove themselves. The owner cannot be removed (unless project is transferred, out of scope).
- **Cleanup**: Removing an assigned task member unassigns them from active tasks.

Namespace: `/app` (Protected)

- `/app/dashboard`: Aggregated view (projects overview).
- `/app/projects`: List of all projects.
- `/app/projects/new`: Create a new project form.

## TANSTACK QUERY STRATEGY

**Projects**:
- `useQuery` for project lists (`projects`).
- `useQuery` for project details (`project`, `projectId`).
- `useMutation` for create/update/delete, invalidating the respective lists/details.

**Tasks**:
- `useQuery` for task lists (`tasks`, `projectId`).
- `useMutation` for create/update/delete tasks, invalidating task lists.

**Kanban**:
- Backend remains the source of truth.
- Optimistic UI updates should be used for drag-and-drop status changes to ensure a snappy user experience.
- If the `PATCH /api/tasks/:taskId` mutation fails, the optimistic update must be rolled back.

## KANBAN REQUIREMENTS

- **Columns**: To Do, In Progress, Review, Done.
- **Status Persistence**: Dragging a task updates its `status` via `PATCH /api/tasks/:taskId`.
- **Ordering**: No complex manual ordering/ranking is required for Module 2. Status persistence is sufficient.
- **States**: Loading skeletons, empty column states, and error toasts for failed drops.

## ERROR HANDLING

Expected standardized API errors:
- `400 Bad Request`: Validation errors.
- `401 Unauthorized`: Missing or invalid token.
- `403 Forbidden`: Authenticated, but lacks project membership/ownership.
- `404 Not Found`: Project, task, or user does not exist.
- `409 Conflict`: Duplicate membership.

Internal errors must not expose stack traces or MongoDB details in production. Frontend must present user-friendly toast/alert messages.

## SECURITY

- Enforce authorization checks on every backend operation referencing a `projectId` or `taskId`.
- Validate all ObjectIds before querying the database.
- Do not trust client-supplied user IDs; always verify against `req.user.id` or project membership arrays.
- Avoid mass-assignment by explicitly picking allowed fields from `req.body` in controllers.
- No cross-project task access.

## PERFORMANCE / INDEXING

**Project Indexes**:
- `owner`: Fast lookup for user's owned projects.
- `members`: Fast lookup for user's accessible projects.

**Task Indexes**:
- `project`: Fast retrieval of all tasks for a board.
- `status`: Helpful for filtering tasks by column.
- `assignee`: Helpful for "My Tasks" views.

## EMPTY / LOADING / ERROR STATES

- **Empty**: "No projects yet. Create one to get started." / "No tasks in this column."
- **Loading**: Skeletons matching the Kanban board UI layout.
- **Error**: Graceful fallback UI or toast notifications (e.g., "Failed to load project").
- **Unauthorized**: Clear "You don't have access to this project" screen instead of a blank page or raw JSON.

## RESPONSIVE DESIGN

- **Desktop**: Full Kanban board view.
- **Tablet/Mobile**: Kanban columns may need to be scrollable horizontally or stacked vertically.
